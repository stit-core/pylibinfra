# authnkit — конфигурация

Три публичных конфига: `Argon2idParams` (параметры хэширования), `JWTConfig`
(секрет, TTL и leeway токенов) и `TOTPConfig` (issuer и окно TOTP). Все —
**part of public API**: имена полей, их типы и env-alias'ы менять = breaking
change (см. [корневой README § Версионирование](../../../../README.md)).

Все три — `pydantic-settings.BaseSettings` с общим `model_config`: поле
заполняется и по имени, и по ENV-alias'у; заданная, но пустая переменная
читается как незаданная; конфиг после валидации неизменяем (`frozen`).

Валидация — сама модель: значение вне окна отвергается при построении.
ENV-фабрики (`new_argon2id_params` / `new_jwt_config` / `new_totp_config`)
переводят ошибку pydantic в `authnkit.ConfigError` с текстом
`authnkit: invalid config: <ENV>: <причина>` и **без значений полей**.
Конструкторы примитивов (`Argon2idHasher`, `HS256JWT`, `TOTP`) проверяют окно
ещё раз и поднимают `ConfigError` — конфиг, собранный в обход pydantic
(`model_construct`), не доезжает до первого запроса.

Прямой вызов `Argon2idParams(...)` / `JWTConfig(...)` / `TOTPConfig(...)`
поднимает pydantic `ValidationError` (это тоже `ValueError`). pydantic печатает
в текст такой ошибки исходное значение поля, поэтому секрет читай
`new_jwt_config()`: там значения полей вырезаны.

RBAC конфига не имеет: `Registry` наполняется кодом через `register`.

## Argon2idParams

Параметры Argon2id. Передаются в `Argon2idHasher(params)` напрямую либо
читаются из ENV через `new_argon2id_params()`.

| Env | Поле | Тип | Default | Назначение / правило валидации |
|---|---|---|---|---|
| `ARGON2_TIME` | `time` | `int` | `3` | Число итераций (passes), окно `1..64`. Растит CPU-стоимость линейно. |
| `ARGON2_MEMORY_KIB` | `memory_kib` | `int` | `65536` | Память на один хэш, в КиБ (`65536` = 64 МиБ), окно `8192..1048576`. Главный рычаг стойкости. |
| `ARGON2_THREADS` | `threads` | `int` | `4` | Параллелизм (lanes), окно `1..16`. Обычно = числу ядер. |
| `ARGON2_KEYLEN` | `key_len` | `int` | `32` | Длина выходного ключа (хэша) в байтах, окно `16..128`. |
| `ARGON2_SALTLEN` | `salt_len` | `int` | `16` | Длина случайной соли в байтах, окно `8..64`. |

Сверх поштучных границ действует потолок стоимости: `time * memory_kib` не
больше `MAX_COST_KIB_PASSES` (786432 КиБ·прохода). Окно значений одно и для
`hash`, и для `verify` (константы `MIN_TIME`, `MAX_TIME`, `MIN_MEMORY_KIB`,
`MAX_MEMORY_KIB`, `MAX_COST_KIB_PASSES`, `MIN_THREADS`, `MAX_THREADS`,
`MIN_SALT_LEN`, `MAX_SALT_LEN`, `MIN_KEY_LEN`, `MAX_KEY_LEN`): параметры хэшера
вне окна → `ConfigError` на старте; PHC-строка вне окна → `verify` поднимает
`HashParamsError` до вычисления Argon2.

`MAX_COST_KIB_PASSES` ограничивает произведение `t * m`, а не каждый параметр
по отдельности: одна проверка стоит не больше четырёх дефолтных хэшей по CPU и
не больше 768 МиБ по памяти, какой бы ни была строка в хранилище. Из-за него
`ARGON2_MEMORY_KIB` = 1 ГиБ недостижим ни при каком `t` ≥ 1 — практический
потолок памяти 786432 КиБ (при `ARGON2_TIME` = 1).

`key_len` и `salt_len` влияют только на новые хэши: при `verify` фактическая
длина ключа берётся из самой PHC-строки, а соль — из неё же, поэтому изменение
этих полей не ломает проверку ранее выданных хэшей. `needs_rehash` сравнивает
все пять параметров строки с параметрами хэшера.

## JWTConfig

Секрет, сроки жизни токенов и leeway. Передаётся в `HS256JWT(cfg, …)` напрямую
либо читается из ENV через `new_jwt_config()`.

| Env | Поле | Тип | Default | Назначение / правило валидации |
|---|---|---|---|---|
| `JWT_SECRET` | `secret` | `SecretStr` | — (обязателен) | Общий HMAC-секрет для подписи и проверки HS256. Короче 32 байт → `ConfigError`. |
| `JWT_ACCESS_TTL` | `access_ttl` | `float`, секунды | `900` (15 мин) | TTL для `sign_access`. Должен быть `> 0`. |
| `JWT_REFRESH_TTL` | `refresh_ttl` | `float`, секунды | `2592000` (30 суток) | TTL для `sign_refresh`. Должен быть `> 0`. |
| `JWT_LEEWAY` | `leeway` | `float`, секунды | `60` | Допуск рассинхрона часов при проверке `exp`/`nbf`/`iat` в `parse`. Должен быть `>= 0`. |

`sign(claims, ttl)` принимает TTL явно — для токенов с нестандартным сроком
(одноразовые ссылки, приглашения); `ttl <= 0` → `ConfigError`.
`sign_access`/`sign_refresh` берут TTL из конфига. Пороги и дефолты доступны
константами: `MIN_SECRET_LEN` (32), `DEFAULT_ACCESS_TTL`, `DEFAULT_REFRESH_TTL`,
`DEFAULT_LEEWAY`.

`iss`/`aud` конфигом не задаются — это аргументы конструктора `issuer=` /
`audience=` (см. [usage.md](usage.md)): они одновременно проставляются при
подписи и требуются при разборе.

Секрет хранится как `SecretStr`: в `repr`/`str` конфига и в тексте
`ConfigError` его значения нет.

## TOTPConfig

Передаётся в `TOTP(cfg, …)` напрямую либо читается из ENV через
`new_totp_config()`.

| Env | Поле | Тип | Default | Назначение / правило валидации |
|---|---|---|---|---|
| `TOTP_ISSUER` | `issuer` | `str` | — (обязателен) | Имя сервиса в otpauth-URL (показывается в authenticator-приложении). Пустой или с `:` / `/` → `ConfigError`: label URL стал бы неоднозначным. |
| `TOTP_SKEW` | `skew` | `int` | `1` | Сколько соседних 30-секундных окон принимается с каждой стороны: `1` → код живёт ~90 с, `0` → только текущее окно. Окно `0..2` (`MAX_TOTP_SKEW`), выше → `ConfigError`. |

Период (30 с, `TOTP_PERIOD`), число цифр (6, `TOTP_DIGITS`) и алгоритм (SHA1) —
константы кита, одинаковые в `generate` и `verify`; конфигурировать их незачем,
authenticator-приложения ждут именно эти значения.

## Тюнинг стойкости Argon2id

Дефолты (`t=3, m=64 МиБ, p=4`) — разумная отправная точка для интерактивного
логина на сервере общего назначения. Калибровка — под целевое время одного
`hash` (ориентир — 50–250 мс на проде; меньше — слабо, больше — DoS-поверхность
на всплеске логинов).

- **Главный рычаг — `ARGON2_MEMORY_KIB`.** Память дороже всего для атакующего на
  GPU/ASIC; поднимай её в первую очередь, держа `time` небольшим.
- `ARGON2_TIME` — добивка, когда память упёрлась в RAM-бюджет инстанса; потолки
  окна (`MAX_TIME` = 64, `MAX_COST_KIB_PASSES` = 786432) на порядок выше любой
  разумной калибровки и существуют ради строк из хранилища, а не ради тюнинга.
- `ARGON2_THREADS` ≈ числу доступных ядер; не превышай, иначе lanes сериализуются.
- Замеряй на целевом железе: `hash` — единственная операция кита, стоимость
  которой задаёшь ты, и она же определяет, сколько логинов в секунду выдержит
  инстанс (каждый занимает поток из пула `asyncio.to_thread` на всё время
  вычисления).
- Поднятие параметров безопасно для уже выданных хэшей: они проверятся на старых
  параметрах (зашиты в PHC-строку). Перевыпуск под новую стойкость — на
  следующем успешном логине: `verify` → `needs_rehash` → `hash`; кит не делает
  этого автоматически.
