# Профиль репо для /plan — pylibinfra

- **Роль:** библиотека. Не форкается: `telegram-bot-template` и его форки тянут пакет из git по тегу
  (`[tool.uv.sources]`, `rev = "vX.Y.Z"`). Сюда приходят прямым заходом или с задачей из бота (новая
  инфра-механика через `/infra-handoff` бота). Если вместе с китом нужно менять и потребителей, это
  программа в хабе `<org>/infra`, а здесь — её фаза библиотеки.
- **Гейт перед «готово»:** `make check`; перед тегом — `make gate-clean` и `make test-full`.
- **Проверка планов:** `make plan-check` (входит в `make check`, поэтому и в pre-push).
- **Сводка планов:** `make plan-check A=--summary`.
- **Типовые проверки шагов:** `uv run --no-sync pytest tests/<kit> -q` → passed · `make test-full` →
  passed (нужен Docker) · `make typecheck` → mypy без ошибок · `make envdoc-check` → OK ·
  `make check` → зелёный.
- **Handoff:** потребителям — через аннотацию тега (`/release`: «Breaking» по китам — что
  изменилось и как мигрировать). В плане раздел `## Handoff` перечисляет, что потребитель делает
  при обновлении; при релизе это уходит в аннотацию.
- **Разбор падений:** отдельного скилла нет — сначала регрессионный тест, воспроизводящий дефект,
  потом фикс (CLAUDE.md § Границы).
- **До плана выясни:**
  - какие киты затронуты и меняется ли public API — сигнатуры, имена полей и `validation_alias`,
    дефолты, имена метрик: breaking идёт minor'ом с `!` в коммите и строкой миграции в аннотации тега;
  - паритет с `golibinfra`: те же имена китов, ENV и метрики — если меняется Go-аналог, что
    меняется здесь;
  - нужна ли новая зависимость или extra в `pyproject.toml` — она уезжает в граф каждого
    потребителя, решение за пользователем;
  - каких потребителей это касается (бот и его форки) и что им придётся сделать;
  - observability нового поведения: метрики, спаны, health-проба, README кита (`make envdoc-check`
    сверяет конфиг с доками);
  - нужен ли testkit-сабпакет; для нового кита — это работа `/add-kit`.
